# Slice 4 PR 2: standalone technical diagnostics validation

This PR adds pure `technical_diagnostics_v1` JSON validators only. Nothing registers a Gateway task, authorises an operator, collects evidence, invokes a model, or executes advice. Slice 3 policy, runtime, worker, database and production configuration remain unchanged.

`validateDiagnosticInputV1(rawJson, nowMs)` accepts a platform content bundle, a component of the future server envelope. It is not the full readiness envelope or proof of operator authority. `validateDiagnosticOutputV1(rawJson, submittedInputJson, nowMs)` revalidates the original bundle and binds results to its request ID and digest. Both return `{ ok: true, value }` or `{ ok: false, error: { code, path } }`; failures omit submitted content.

All fields are required and unknown fields are rejected at every object level. Inputs accept only platform scope, platform_internal or restricted classification, seven allowlisted evidence kinds and text/plain content. Restricted evidence requires restricted bundle classification. Evidence IDs are unique. Provenance requires a bounded kind-specific reference, immutable revision, sanitisation version 1 and UTC timestamps. Repository revisions accept 40 or 64 lowercase hex characters; report revisions require 64. Evidence capture must precede creation and be at most 24 hours old at the explicit validation clock. Submission lifetime is at most five minutes; expired submissions fail.

Each contentSha256 is SHA-256 of exact UTF-8 content. bundleSha256 is SHA-256 of the bundle with that field omitted, serialised with recursively sorted object keys, original array order and JSON string escaping. No Unicode or whitespace normalisation is applied to content. Digests establish identity, not truth or trusted provenance. Duplicate JSON keys, including escaped equivalents, fail before parsing can collapse them.

Limits: 32 KiB encoded input and output, 16 evidence items, 2 KiB UTF-8 per text field, 10 findings and recommendations, 16 limitations and missing-evidence items, 10 verification steps per recommendation and 40 total. JSON depth is capped at 16 and parsed nodes at 4096. No truncation occurs. Token budgets, transport allocation and tokenizer admission are future runtime responsibilities.

Findings require unique IDs, allowlisted severity/confidence and at least one exact citation. Citation start/end are half-open UTF-16 offsets in supplied content; quotes must match exactly. Recommendations reference existing findings and require requiresHumanReview=true. Recommendations status requires findings and recommendations. Other statuses prohibit recommendations and require limitations; insufficient_evidence also requires missingEvidence. Model output cannot supply execution provenance; that must be independently server-attested in a future integration.

Recognised embedded instruction, executable payload, secret and personal/customer-data patterns are rejected in content and result text. These heuristics can produce false positives and cannot prove sanitisation, detect every secret/customer record, eliminate prompt injection or establish semantic support for claims. Trusted collection, sanitisation, operator authority, safe rendering and inert handling of advice remain required before integration. Schema-valid citations alone do not establish factual correctness. This PR does not claim the full readiness acceptance matrix or activation approval.

Run `npm run test:technical-diagnostics-validation` for synthetic-only contract tests. No customer fixtures, credentials, network requests or model calls are used.
